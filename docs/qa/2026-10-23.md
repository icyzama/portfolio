Lint and the production build passed. The HTTP and isolated contact-handler checks completed with **45 passed, 5 failed across 50 checks**. These failures represent two findings; four failing cases exercise the same validation defect. The rate-limit diagnostic also reproduced the existing header-trust concern.

- Checked HTTP responses, page titles, main landmarks, and primary headings for all seven page routes.
- Resolved 11 internal link targets and fetched 58 unique local asset URLs referenced by server HTML. This verifies responses, not browser appearance or client-side navigation.

This is partial QA, not complete browser sign-off.

## Findings

### P2: Contact accepts inherited property names as enum values

The topic and timeline label lookups use ordinary JavaScript objects without checking that a supplied key is an own property. Truthy inherited properties therefore pass validation.

Reproduction in the isolated handler:

1. Supply otherwise valid contact fields: a name, email, message, and topic.
2. Set `topic` to `constructor`, `__proto__`, or `toString`.
3. Alternatively, use `topic: project` and `timeline: constructor`.

Expected: HTTP 400 and no call to the email provider.

Actual: HTTP 200 and a call to the mocked provider, with an unintended label in the email.

Evidence: `src/app/api/contact/route.ts`, topic lookup at line 63 and timeline lookup at line 72. Four failed checks cover these cases. Enforce membership in the actual supported values before constructing an email. These tests demonstrate an allowlist bypass, not prototype pollution or arbitrary code execution.

### P2: Experiences content is absent from server HTML

Fetching `/experiences` returns HTTP 200 but no primary heading or organization content. The response contains `Loading experiences` and a `BAILOUT_TO_CLIENT_SIDE_RENDERING` marker. The other six pages include a primary heading in server HTML.

Expected: The default Experiences view has useful server-rendered content, with query-driven tabs enhanced on the client.

Actual: The entire view is within a Suspense boundary around a component using `useSearchParams`. Without client JavaScript, the view remains a loading fallback. This also makes content less available to consumers that do not execute JavaScript.

Evidence: `src/app/experiences/page.tsx`, Suspense boundary at line 7; `src/features/experiences/experiences-page.tsx`, search-parameter access at line 20. This is a server-rendering/progressive-enhancement finding; normal hydrated browser behavior was not tested.

### Existing issue #5: Forwarded-header bucket selection reproduced

Five mocked sends from one supplied `X-Forwarded-For` value are allowed; the sixth is rejected with HTTP 429. Changing only that header allows another send. The handler-level behavior is confirmed. Whether a remote caller can do this on the deployed site depends on the proxy's header sanitization. A production exploit has not been established.

## Repeating the checks

From the repository root, run `npm run build`, then in another terminal run `npm run start -- --hostname 127.0.0.1 --port 3000`. With that server running, run `node scripts/qa.mjs`.

The QA script uses only built-in Node modules and the project's existing TypeScript dependency. It performs safe invalid-request checks against the local server and mocks email delivery for all valid submissions. It exits with status 1 when checks fail and writes detailed results to `.next/qa-results.json`. The captured results from this run are in `docs/qa/2026-10-23-results.json`.
